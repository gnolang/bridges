## Findings

### S-22 · medium-low · `Execute` reads the client's head for every kind, so a client whose head version is not 1 bricks every decision — the corrective kind 8 and a kind 9 included — with no path left but a new deployment
`admin-program/src/processor.rs:680` (`let head = client_head::read_checked(client_state, &CLIENT, CLIENT_STATE_VERSION)?;` before the kind dispatch; `head` is read at `:681` alone, for `recovery::window_stands` of a recovery decision), `sol-util/src/client_head.rs:86-88` (`head.version != version → InvalidAccountData`), `admin-program/src/recovery.rs:328` (`record` reads `client_body`, which it needs for the digest's chain id), `:128` (`settle`), `gno-light-client-ism/src/processor.rs:64-72` and `sol-util/src/client_head.rs:31-50` (the client's own paths never check the version byte, so a client whose head says 2 keeps running and keeps verifying decisions). The pausable ISM's refusal (`pausable-ism/src/processor.rs:298`) is the intended fail-closed; the admin program's is not — the only cure for a wrong client build is a decision this read refuses.

Scenario: §13's kind-4 route run in the wrong order. A new client layout is "a successor admin program and pausable ISM, by kind 9, built to read it and transferred before the client's upgrade" — two proposals, and the order is GovDAO's to keep; nothing on chain or in `hlwatch`'s kind-8 check reads a client buffer's layout contract. The client's kind 8 lands first (its migration writes the new version byte into the head, as a layout change must, for the readers that pin it); the kind 9 to the new pair is pending, or not yet proposed. From then on the pausable ISM refuses every delivery (by design), and the admin program: every `Execute` of a non-cancelled decision fails at `:680` whatever its kind and channel — the kind 8 that re-upgrades the client from a fix build (the mailbox channel, which needs no client read), a kind 9 to a successor built for the new layout, a kind 11 — and every `RecoveryRecord` fails at `:328`. Decisions keep arriving (the client's `Verify` and `Handle` still work) and pend for good; cancels still close them. The deployment ends (§1), and the one decision that would have cured a mistake cannot run. Not a forgery: a liveness end with no exit, reached by one approved build.

Fix: move the read under `if is_recovery` — `let head = if is_recovery { Some(client_head::read_checked(…)?) } else { None }` and pass it to `window_stands` — one line moved; mailbox-channel decisions then never read the client, so a kind 8 of a fix build (a client that writes version 1 back) or a kind 9 executes and the recovery path returns with it. Have `hlwatch`'s kind-8 pre-vote check for the client program say that the layout contract (§13, kind 4) is the build's to keep and print the buffer's hash beside the reproducible fix build's. A test: the client's head version byte doctored to 2 in the bank, a mailbox kind 8 for the client executing, a recovery `record` refused.

### S-23 · medium-low · kind 9 hands everything to a successor whose compiled clock factor it never reads, so a devnet-factor successor on mainnet runs every brake eight times faster — the guard `finish_setup` gives the launch programs (S-06) is not on the successor's path
`admin-program/src/processor.rs:89-98` (`can_inherit`: owner, parse, `predecessor`, `inherited`, `successor` — the parsed `State` carries `clock_factor` at byte 1 and it is not compared), `:313-328` (`finish_setup`'s S-06 check of the three factors, which a successor reaches only after the hand-over and which nothing requires of it: "cosmetic", round 5), `admin-program/src/config.rs:46` (`CLOCK_FACTOR` per build), `recovery.rs:63-65`, `:73`, `:146`, `kinds.rs:290-296`, `processor.rs:700` (every clock of the admin program — the grace, the week, the fortnight, the 21 days — divides by its own factor; `pausable_hold` judges the pausable ISM's hold with the admin program's grace, not the pausable ISM's); `bridge/cmd/hlwatch/main.go:493-556` (`successorCheck` reads the predecessor, the inheritance, the layout, the pending counts, the counters and the upgrade authority — never `ClockFactor`); PLAN.md §5.9/§8.3 ("1 on mainnet; a devnet build is 8").

Scenario: the successor build for a new client layout (§13's kind-4 route) is compiled with `FACTOR8=1` by mistake — the devnet drill's build, deployed and initialised on mainnet, burned, proposed; its hash matches what the proposer built. `hlwatch` says "immutable … the version-1 layout, nothing pending: kind 9 can execute". Kind 9 executes: every authority is the successor's. From then on the 7-day group matures in 21 hours, a replacement's 21-day floor is 63 hours, a hold opens the validators' window in 42 hours, a lapse in 42 hours, the grace is 3 hours — and the successor reads the pausable ISM's 24-hour hold as ended 3 hours into a dip, so `settle` records a set the pausable ISM still holds against. The brakes the plan prices in days are hours, unseen (nothing prints the byte before the vote; `hlsol audit` prints it for the launch program, where `finish_setup` refused the mismatch). S-06 made this an on-chain refusal for the launch; the successor path reopened it.

Fix: in `can_inherit`, `s.clock_factor == CLOCK_FACTOR` (this build's, which `finish_setup` proved equal to the client's and the pausable ISM's) — one condition, the transfer spent otherwise like the other cannot-inherit cases; `hlwatch`'s `successorCheck` prints the successor's factor beside the client's and alarms a difference (the Go lane's). A test: the successor's `clock_factor` doctored to 8 in the bank, the kind 9 spent with every authority untouched.

### S-24 · medium-low · a kind 9 carried by a hold-opened recovery executes under the hold, and the hand-over drops that hold: the moment it executes, anyone's `Settle` on the successor records the set the hold was blocking, and the honest validators' window on the successor is gone
`admin-program/src/processor.rs:696-707` (a recovery decision with `trigger == TRIGGER_HOLD` is `like_mailbox == false`: no deferral, so a kind 9 executes while the hold stands — the only way kind 9 ever executes under a hold, since the mailbox channel's is `Deferred` at `:703-706`), `:926-944` (the hand-over sends `seats`, `watch`, `settled` and `holds` — the ended holds — never the standing one), `:201` (`successor_init`: `Guardians::new(seats, watch)`, flags none, `hold_since` none), `recovery.rs:79-84` (`settled_set` on the successor reads the pausable ISM's hold and the *caller's own*, which is none), `:111-141` (`settle`: permissionless, records the client's newest settled entry when its from-height is newer than the inherited record), `:143-156` (`window` on the successor: a hold-opened window needs a hold on the successor 14 days old — a new one), `state.rs:39-45` (`holds` is "the holds that ended"). PLAN.md §6.5: a successor "with no flags, no hold and no pending decisions (the transfer is itself the cure a hold waited for)"; §6.4: the recovery "may sign any decision the admin program accepts … the mailbox kinds too", the drill "including a transfer to a successor"; M2-NOTES choice 5: "the reset is the last decision of a recovery procedure … the validators' tool orders it last". Nothing in the suite carries a kind 9 through the recovery channel (every kind 9 is `w.decide(9, …)`, the mailbox's; admin.rs:1962 is the refused staging of S-20).

Scenario (the S-01/S-20 premise): a thief with the current set's keys rotates the client to his own; the guardians hold the admin program — by hand, the one flag that opens the validators' window, not the pausable ISM's (deliveries are quarantined already; the one-stroke flag is `hlwatch`'s habit, not a program rule); a week on his set's quarantine ends, blocked from settling by that hold (`h.time ≤ quarantine_end`), the record stays the honest set. Fourteen days on the honest set's window opens; the recording path is the suspected bug, so they carry a kind 9 to a successor S by recovery, ordering the reset last as choice 5 says. The kind 9 executes under the hold. In that transaction, or the next, the thief sends `Settle` on S: S has no hold, the pausable ISM has none, the thief's entry is past its quarantine → S's record is the thief's set. The reset pending on P is dead (P retired); re-staged on S it needs S's recorded set's signatures — the thief's. The honest validators have no recovery on S; the guardians dare not hold S (a hold there opens the thief's window in 14 days) and keep one lone flag to defer his forged decisions: §1's stand-off, with every authority under S. Even with the one-stroke flag standing on both objects (the thief's set then stays blocked), the honest validators' window on S opens only 14 days after they re-hold S — a fortnight the plan does not count, during which the thief feeds headers so no lapse opens.

Fix (smallest, on chain, nothing deployed yet): the hand-over carries the predecessor's `guardians` whole — keys, flags, `hold_since`, `dip_since` — in place of `seats` and `watch` (the `Guardians` layout is already in the state pin; re-pin `SuccessorInit`), so the hold that opened the window stands on S as it stood on P: `settle` on S is blocked as on P, `window` on S opens at once (the carried start is 14 days old), and a mailbox kind 9 carries nothing (a flag or a hold defers it, so it executes with none). §6.5's "no flags, no hold" becomes "the predecessor's flags and standing hold as they stand at the transfer". Interim, in the tools: `hlrecover` orders a kind 9 after the reset (the reset executed first on P settles the honest set and clears the thief's entry from the client's history, so S's `Settle` finds nothing newer) and refuses to stage one under a hold that stands on the admin program alone; `hlwatch` alarms a hold on one object without the other. A test: a kind 9 recorded under a hold-opened window and executed under the hold, then `Settle` on S with a quarantined-then-past entry in the client, the record unchanged and S's window open.

### S-25 · low · the successor's authority PDA starts with no lamports and the predecessor's float is stranded, so the first kind 6 on a successor waits on a hand
`admin-program/src/processor.rs:798-806` (kind 6's CPI, whose realloc top-up Hyperlane draws from the owner — the authority PDA, writable, M2-NOTES 17b: ≈0.0005 SOL an enrolment), `:861-947` (kind 9 moves nine authorities and writes the successor's state; no lamports move, and no instruction of the admin program ever moves the PDA's lamports); `bridge/cmd/hlsol/setup.go:786-793` (the launch PDA funded to `authorityFund`), `bridge/cmd/hlsol/main.go:272-306` (`successor-init`: the init and the burn, no funding); PLAN.md §6.5 "so no decision ever waits on the operator's hand".

Scenario: kind 9 executes; GovDAO's next kind 6 (a route's migration, §5.3) reaches the successor and matures; its `Execute` dies in Hyperlane's `EnrollRemoteRouters` for want of the top-up (the successor's PDA holds 0) and pends for a retry until someone sends it lamports — nothing in the tools does, and the predecessor's remaining float (0.01 SOL, twenty enrolments' worth) can never leave its PDA.

## Checked and held

- Signers, owners, seeds: every state read goes through `load_state`/`check_state`/`own` (owner and the canonical seed); a decision by owner, address and its own channel/number; a stage by owner and version, and by its submitter for every write; the authority PDA by `create_program_address` with the stored bump; the mailbox's process authority by seed under the compiled mailbox. Every CPI the PDA signs targets a compiled program id, the loader, or the successor `can_inherit` admitted, and the runtime matches the program account the executor passed against it. A `Verify` of the pausable ISM runs only inside the mailbox's `InboxProcess` of the same bytes (the sysvar's current index is the top-level instruction's, so a wrapper or a direct call is `NotTheMailbox`); the charge is written before the client's CPI and reverts with it; a recipient that is no token is unmetered.
- Aliasing: a cancel pair naming one decision twice is a no-op the second time (closed, system-owned); the state, a stage or a cancel record where a decision is expected fails the address check; the state parsed as a stage fails its submitter; the deliverer, submitter and closer are keys the program recorded or that signed.
- The precompile: program id, count, zero padding, self-referencing indices, every offset inside the data, the message equal to the digest or the sign bytes; a duplicate slot sets a bit twice; a stranger's key fails the slot's compare; the runtime verified every (key, message, signature) before any program ran.
- Header, merkle, vote against tm2 and §13: the sixteen leaves with `bytesOrNil`, the canonical vote's six fields (fixed64 height and round, the part set's uvarint Total, the time's two uvarints, the length prefix), `getSplitPoint`, `computeHashFromAunts` taking the aunts leaf-first and demanding the exact count, the validator leaf and the address order, `MaxTotalVotingPower`; seventeen real heights pinned (every hash and set, 60+ signatures, the three set changes, `LastResultsHash` from re-encoded results, the §13 example byte for byte).
- The commit rule: by slot, one round, `3·tallied > 2·total` in i128, nil or other-block precommits never staged, the set bound at the staging by hash and length and re-checked at the finish; the announcing header must be presented; a stage staled by a set change dies at `WrongSet`; the ring cleared and the epoch bumped at a change and a reset; the settled anchor never evicted.
- Holds and settlement: `hold()` pure; the dip rule and the grace; the floor from the history (a merge can only lower it); `note_hold_end` at every change; the quarantine extended by overlap and cleared only by a reset; `settled_set` blocked by a hold on either object whose start is at or before the end.
- Recovery: the hold window over the lapse; the anchor per window; the digest over the counter the decision will take; `StaleStage` on a moved record or another digest; the cancel record's own allocation; ranges clamped at the channel's last number; pending counts and pruning; kind 10 strictly above the high-water mark by at most 2^32; a reset's parameters the client would refuse spent, never pending on a CPI.
- Kinds 8 and 9: the hash over the buffer's bytes after the loader's header; `NeedsExtend`; the refund key by construction; the self-cases and the cannot-inherit cases spent before any CPI; the hand-over's order and the retirement.
- Rent and realloc: every growth at most 10,240 bytes with a signer paying; the state reserves 64 ranges, 128 validators, 8 holds and `successor: Some`; a decision at most 10,240; a pre-funded PDA address topped up, allocated and assigned; the client never shrinks.
- Fail closed: every parse error is an error, never a default; unknown kinds spent; a failing CPI leaves the decision pending; saturating clock sums; checked power sums.
- Compute and the clock factor: nothing new on a hot path; each crate's own `CLOCK_FACTOR`, the admin program never reading the two library crates' constants; the launch programs' bytes compared by `finish_setup`; the suite green at both factors.

## Verdict

Round 5's two fixes hold at their lines, and M2h's choice of which entries to refuse is the right one — every entry it left needs something an un-inherited successor cannot have. Nothing above medium. Three medium-lows and one low, all at the edges of the hand-over and the client's layout pin: `Execute` reads the client's head for every kind, so the plan's own layout route run in the wrong order bricks the admin program with no exit (S-22, one line moved); kind 9 never reads the successor's clock factor, so a devnet-factor successor runs every brake eight times faster (S-23, one condition); the hand-over drops the hold that opened a hold-carried kind 9's window, so a thief's set can settle on the successor at anyone's `Settle` (S-24, the guardians carried whole); a successor's PDA is unfunded (S-25, a tool step). None forges a header, a proof, a charge or a decision; none reuses a number or moves a hold. With S-22 and S-24 folded the programs converge.
