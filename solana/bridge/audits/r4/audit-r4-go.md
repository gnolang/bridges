## Findings

### G28 — high — every transaction read pins the RPC to version 0: a v1 transaction (SIMD-0385, on mainnet since 2026-09-15) is unreadable by every scanner, and one of them blinds the record, the index and `flag -ids` for good
agent/chain.go:621-622 (`v := uint64(0)` … `MaxSupportedTransactionVersion: &v` in `solDispatchesIn`), agent/record.go:252-253 (the same in `transactionInstructions`; `RecoveryLog.Sync` rides it, recovery_views.go:150); chain.go:530-533 (a read error becomes a `scanSkip`, retried every round for ever), record.go:199-203 (a read error returns before the cursor moves), monitor.go:838-840 (`len(Skipped) > 0` mutes `unindexedCredits`), views_sol.go:315-317, 361 (hlwatch lists the skip as unconfirmed, the Forged section off), cmd/hlwatch/main.go:1047-1049 (`flag -ids` refused on it). solana-go v1.25.0 decodes v1 (`message.go:103, 521`); the RPC refuses to return one under a pin of 0 (-32015, "not supported by the requesting client").
Scenario: a griefer sends one v1 transaction moving a lamport to the client's state PDA (any account takes lamports; it succeeds and `getSignaturesForAddress` lists it). Every monitor's and hlwatch's `Sync` errors at it on every poll before the cursor passes it: the record stays "behind", `header:gap`'s sighting is cleared, the error is a log line — §5.9's fork and gap rules are blind from then on, silently, for 5,000 lamports. A second v1 transaction that merely names a token program parks a permanent skip on every signer, relayer, monitor and hlwatch: `scan:unreadable` hourly for good, the unindexed-credit rule muted, every guardian's `flag -ids` refused. And a user whose wallet sends `TransferRemote` in a v1 transaction has burned coins no signer ever indexes: never signed, never credited.
Fix: `MaxSupportedTransactionVersion` = 1 at both call sites (the library already decodes v1); a test folding a v1-shaped `GetTransactionResult`; and name an RPC "not supported by the requesting client" answer as a build gap in the skip's alarm, never a transient.

### G29 — medium — a transaction a provider cannot read stalls the record scan for ever with no alarm: a fresh hlwatch or monitor on a provider without full history never builds the record
agent/record.go:195-209 (`Sync` returns at the first unreadable transaction, `Cursor` unmoved); monitor_sol.go:64-66 (`solErr` logs; an alarm only for `errProviders`), 72-78 ("behind" clears the `header:gap` sighting); views_sol.go:426 (`confirmed` appends to `v.Err`); cmd/hlwatch/main.go:816-818, 937-942 (`diff` alarms on `Unconfirmed`, never on `Err` or `SolErr`).
Scenario: a guardian installs hlwatch a year after launch (no state file) on a provider whose `getTransaction` keeps 90 days: `signaturesSince("")` lists every transaction since the deploy, the oldest answers null, `Sync` errors there on every poll, the record is "behind" for good. `status` prints one "not read" line; `watch` alarms nothing; that machine never compares a client header with gno.land's. The operator's monitor after a lost state file is the same. G28's lamport is this stall with a cause anyone can plant. §5.9's "a scan still behind the snapshot is no verdict" meant a catch-up, not a wall.
Fix: alarm a `Sync` error that persists two minutes (`persist("record:scan", …)` in the monitor; `v.Err` → an alarm in hlwatch's `diff`); let a fresh install start from a checkpoint — the client's current `Records`, `RunningHash` and slot as the base (`-record-from`), folded forward, as the trusted header is taken.

### G30 — medium — a monitor poll that fails past step 2 alarms nothing: an hour without a verdict is a log line and a status field
agent/monitor.go:216-222 (`Run` logs a failed poll and sets `LastErr`); 328-348, 356-359, 399-404 (`mailboxAt`, `routeAt`, `index`, `deliveredAt`, `divertedCredits`, `unindexedCredits` return the error raw); the persisted alarms cover steps 1–2 alone (261, 267, 280, 285).
Scenario: provider 1 rate-limits `getSignaturesForAddress` for an hour, or the own node's `vm/qrender` fails after an upgrade while `/status` answers: every poll returns at step 4 or 5, no identity is judged, `stalls` and `runways` never run, the webhook hears nothing — no key covers a failing poll. The signer under the same outage alarms `signer:no-verdict` and halts within the hour (G7); the monitor, whose silence is read as "nothing to flag", is silent. A break in that hour is caught by the signers alone.
Fix: in `Run`, `m.persist("monitor:no-verdict", "no verdict: "+err.Error(), cutFailAfter)` on a failed poll, `m.clearPersisted("monitor:no-verdict")` on a clean one, and the identity status marked stale.

### G31 — low-medium — after the recipient switch, a decision to the successor is classed "other" for good by a relayer still configured for the predecessor
agent/relayer_sol.go:119-130 (`classify`: a recipient other than `progs.Admin` is `kindOther`, r/hlgov or not), 204-209 (`Done[nk] = "other"`, `GnoNext` advances), relayer.go:295-302 (`pruneDone`), 752-755 (`reemits` skips "other"); config.go:53 (one `solana.admin`).
Scenario: the kind 9 executes, hlwatch shows it, GovDAO's switch lands seven days later, and its first decision to the successor — the replacement of the holders the transfer was for — is dispatched an hour before the operator edits `solana.admin` on both relayers. Both classed it "other" and walked past; after the restart the walk begins at `GnoNext`. It is never delivered; hlwatch shows r/hlgov one ahead with "a foreign decision took a number, or GovDAO's was lost"; the cure, anyone's re-dispatch, is told to nobody, and a hasty `sync sequence` is the wrong one.
Fix: in `classify`, a message from r/hlgov to a program other than the configured admin program is a decision left undone with a note and an alarm `decision:other-program` naming it, never "other"; or read the admin state's `Successor` and deliver to it as a second admin program.

### G32 — low — the foreign-decision rule cannot see an at-once cancel: a foreign cancel racing GovDAO's number cancels silently, and GovDAO's own decision is lost with agreeing counters
agent/views_sol.go:640-647 (`readDecision` nil → nothing compared, `checked = n`); relayer_sol.go:530-566 (`pastDecision`: a processed copy is "recorded", never "taken"); monitor_sol.go:209-213 (`decision:counter` only when `LastSeq > gov.Last`).
Scenario: under a leaked old set, the record rule blinded (G28), the forger watches GovDAO's kind 5 execute on gno.land and lands, seconds earlier, a forged proof of a mailbox `cancel` naming GovDAO's pending replacement under the same number n. The admin program records the cancel, executes it at once, then accepts GovDAO's n and ignores it. r/hlgov's n is a kind 5; the admin program holds no account for n; `foreignFindings` compares nothing; the counters agree; the relayer calls GovDAO's copy "recorded". The replacement is gone and GovDAO's decision lost, silently; only a member reading the pending list notices.
Fix: in `foreignFindings`, when r/hlgov's body at n is of the 7-day group and the admin program holds no account for n inside its week (its cancelled ranges aside), report "number n's decision is gone though r/hlgov's matures in 7 days: a foreign decision took it".

### G33 — low — hlwatch reads out of §5.9's order and trusts a catching-up node; its FORGED CREDIT line has no second-poll patience
cmd/hlwatch/main.go:184-189 (`Status` → H = the head: no `CatchingUp`, no stale check), 226 (`ReadSolanaAt` after it: the snapshot after the gno read), 925-928 (`Flag` on every Forged line each poll); views_sol.go:359-379 (Forged at first sight).
Scenario: the holder's node restarts and catches up: H is an hour old, the supplies are now, the lock at H lacks an hour of sends whose mints the supply holds — `identityDiff` posts BROKEN at flag level. Under a provider whose finalized view lags the signers' by seconds, a fresh claim prints FORGED CREDIT and posts a flag-level alarm for one poll, then clears: noise that trains a holder to ignore the key the rule exists for. ### G34 — low — the claims window is ten pages by address while payouts go by turns: a forged claim at a late-sorting address behind a thousand waiting claims is paid before any poll lists it
agent/chain.go:331-354 (`claimsPageMax` 10, `claims/<from>` from 0 each poll); realm/p/hlroute/v0/hlroute.gno:1886-1898 (`eachWaiting`: recipients by address, each queue oldest first), 601-616 (`Claim` serves the ring from the cursor, one claim a turn).

The exact identity still breaks by 2,400 and flags, after the payout.
Fix: resume the page walk where the last poll stopped and wrap (a per-route offset in the state), so every waiting claim is visited within ⌈N/1,000⌉ polls; or read the ten pages from the cursor's recipient on.

## Checked and held

- The exact identity: over the ordered cut the amounts in flight are exact and a disputed record is out of both sides; a forged credit paid at once still breaks it (the lock and owed fall together, the supply does not), so the index rules are complements and the identity the catch.
- `unindexedCredits`'s gating: a provider's scan error aborts the poll before it, a side list mutes it, one more poll before a flag, a voted claim skipped, an id that turns up clears the sighting and the alarm; the watch key's Solana flag at most once a minute across every condition (`lastSolFlag`), its float on the runway list, so a flap costs ≈0.007 SOL a day and never the week.
- The reservation: the park and every younger message of its token are gated by the same finalized level plus this pass's deliveries; whenever a younger would fit beside the park, the park fits and goes first; a kind 12 raising the cap releases it; the backup's own attempts park it within minutes of the primary's; a park above the day cap (a GovDAO mistake) holds the token for good — the kind-12 builder's check, not the Go's.
- `Retired`: the admin program's code 3031 through `ProgramErrorName`'s disjoint ranges (1000, 2000, 3000), done as "retired", alarmed once, out of the Reemit rule, advancing the walk; a decision dispatched before the kind 9 and attempted after is the same case, re-dispatched under its own number once the successor inherited `LastSeq`; `NotInherited` (3039) parks and retries hourly, right once the kind 9 lands.
- `ExtendTerms`: the preview's numbers are `ExtendBy` on the live program data and buffer and `getMinimumBalanceForRentExemption` at confirmed; a second run answers "no pending decision"; a second extend finds no excess; the relayer's own extend alarms and sends in one tick (stated since round 3).
- `mint:cap-ratio`: units agree (base units on both chains); before `Launch` the lock is 0 and the alarm stands from the first poll — the launch week's picture, as M3g states.
- F14's bound: at 45M gas and the floor, "carried" is 45,000 ugnot, the default bound 1 GNOT, so a node asking up to ≈0.02 ugnot a gas is paid and one asking a whole GNOT a call is parked with its text; the monitor's `SetFlag` through the same `Call` alarms each poll instead of parking.
- The gap rule and the foreign flag after M3g: `ScanSlot = maxSlot` only after a complete fold; `decision:foreign:pending` cleared by a clean poll or by the flag, kept through an erroring poll; a sighting kept while the rule is skipped (`readAdmin` disagreeing) can only flag a finding that stands when the rule runs again.

## Verdict

One high: every transaction read is pinned to version 0, so a v1 transaction — live on mainnet for a month, free to send — blinds the fork and gap rules, mutes the index rule, refuses `flag -ids` and strands a user's burn (G28); a one-constant fix. Two mediums are the same silence from other doors: an unreadable transaction stalls the record scan unalarmed on any fresh install (G29), and a failing monitor poll alarms nothing for an hour (G30). Five lows. Round 3's fixes hold where they were aimed. Fold G28–G30 before devnet; the round-4 Go side returns one above medium.
