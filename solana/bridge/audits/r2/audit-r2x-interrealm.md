## Findings

### X1 — medium — RegisterVerifier takes a sub-realm identity as a registrant; one realm registers verifiers without bound, and the mailbox's json and page walk them all, for good
Rule: Interrealm v2 §5.5 — "Accepting sub-identities is opt-in for callees … PkgPath-keyed auth must use the anchored idiom — a bare prefix also matches sibling and subdirectory packages"; the pinned v1.2.0 VM mints them (uverse.go:177 `Sub`, :185 `Subpath`).
Files: realm/hlmailbox/mailbox.gno:331–347 (`RegisterVerifier`: the caller's only test is `strings.HasPrefix(path, "gno.land/r/")` at 336; `verifiers.Set(path, v)` at 345; no function ever removes an entry), render.gno:104–113 (`summaryJSON` lists every registered path) and 170–179 (the page does); bridge/agent/views.go:45 (`ReadMailbox` reads that json).
Scenario: A realm `gno.land/r/x/spam` runs `sub := cur.Sub(itoa(i)); hlmailbox.RegisterVerifier(cross(sub), v{})` in a loop of its own crossing function: guard 3 of `Sub()` lets a realm mint in its own namespace, and each `cur.Previous().PkgPath()` is `gno.land/r/x/spam#<i>`, a fresh key that passes the prefix test. No package deployment per entry, as round 2 assumed — dozens a transaction, a few hundred GNOT in all. Near 25,000 entries (≈120k gas an entry under the 3B query ceiling) `Render("json")` and `Render("")` fail: the watch's `ReadMailbox` and the page §8.3's member reads are dead and stay dead, since nothing unregisters. `Process`, `satisfiable` and the routes walk `active`, not `verifiers`, so the money paths hold.
Fix: In `RegisterVerifier` refuse a sub-identity — `if cur.Previous().Subpath() != "" { panic("hlmailbox: a realm registers with its own cur, not a sub-identity") }` — so an entry costs a package deployment again; and bound the listing: `json` and the page name at most 20 registered paths with `verifiers.Size()`, the rest at a `verifiers/<from>` path.

### X2 — low — satisfiable hands hlmailbox's own key slice to an unchecked interface implementation; under the no-anchor case an active verifier writes the proposed signer set
Rule: Interrealm v2 §11.3 — "Does it accept an interface or function-value parameter? If yes, gate with canonical-type check"; §4.4 — "When borrow rule #2 doesn't fire on a /p/-method call, the body inherits the caller's m.Realm" (the guide's §3(C)).
Files: realm/hlmailbox/mailbox.gno:331–347 (`RegisterVerifier` keeps any `Verifier` value), 351–363 (`satisfiable(ks)` dispatches `Satisfiable(ks)` on it with hlmailbox's own slice), gov.gno:236 (the creation-time test), 243–244 (`satisfiable(ks)`, then `signerKeys, signerRule = ks, rule` over the same backing array).
Scenario: GovDAO activates a verifier realm whose registered value is a /p/-declared type with a primitive underlying (`type V int`, methods declared in /p/): borrow rule #2 finds no anchor, so `Satisfiable` runs with `m.Realm` = hlmailbox, and `signers[0] = key` commits, `ks` being hlmailbox's. In a removal's closure the write lands before `signerKeys = ks`: a key no proposal named signs for the bridge, and stays after GovDAO swaps the verifier back. hlverifier's /r/-declared `verifier{}` is held to its own authority by borrow rule #1, so the launch verifier cannot; the attack needs GovDAO's 7-day activation of such a verifier, hence low.
Fix: Pass copies — `r.(Verifier).Satisfiable(append([]Key(nil), ks...))` — and say in `Verifier`'s doc that an implementation is a type declared in the registering realm (borrow rule #1), which `RegisterVerifier` cannot check. `Verify` receives hlgnot's bytes, readonly to hlmailbox, so it needs nothing.

## Checked and held

- §5.1/§5.2 `cur` as the capability: every mutator is a crossing function deriving identity from its own `cur.Previous()`; the own-`cur` `IsCurrent()` guards in `caller()`, `propose()`, `Pull`, `Withdraw` and `Execute` are inert ("refuses nobody") and nothing else is trusted; no secondary realm parameter exists in the hl* realms or the p/ packages (checker above).
- ADR "unsafe.* in determining authority is a bug": the only unsafe call is `OriginSend` in hlgnot.TransferRemote (hlgnot.gno:194), paired as unsafe.gno prescribes with `prev.IsUserCall()` (190) and `runtime.AssertOriginCall()` (198), the fee spent by an OriginSend banker minted from the live cur (200); no `unsafe.PreviousRealm`, `CurrentRealm` or `OriginCaller` anywhere.
- §12.1/§12.2 message types: an /e/ realm's Previous has a pkgpath, so `IsUserCall` is false and `AssertOriginCall` panics under MsgRun; the builders are open by design (a request has no effect until the proxy's `PreCreateProposal` admits a member); `mustBeDAO` needs Previous = `gno.land/r/gov/dao`, which only `SimpleExecutor.Execute`, declared there, mints.
- §5.1 and borrow rule #1 on the GovDAO executor: `Execute` gates on the proxy's frame and calls `e.callback(cross(cur))`; every callback is an /r/-declared crossing closure, so it runs under its own realm with `cur.Previous()` = the proxy whoever executes, and that survives an impl upgrade (`Execute` stays in r/gov/dao); no bridge function has the shape `func(realm) error` a member could wrap into an executor.
- §5.3 realm values ephemeral: no closure captures a builder's outer `cur` (each `cb` shadows it); `env(cur)` is built per call inside the executing frame and never stored; `NewSimpleExecutor` keeps `rlm.PkgPath()` only; no realm value in any var, struct, map or `Params`.
- §3.2 storage = authority: `hlroute.New` runs under hlgnot/hlbubble, so every State, Queue, Claim, SweepEntry, Send and Decision is stamped by its route and mutated only through methods on that receiver; `st` and every ledger are unexported; the only pointer out is `Pull`'s fresh `*Snapshot` of value copies with no methods (guide §5.1, §5.1a, §5.1b; review §3, §8).
- §4.1–§4.3 borrow rules on every /p/ mutation from /r/: avl, decisions and hlroute methods on route-stamped receivers borrow to the route; `hlmailbox.Seat` passed as a FuncDecl value and the `Env` closures run under their declaring realm; a registered Verifier's methods run under the registering realm when /r/-declared (X2 is the /p/ exception); direct field writes (`d.Note`, `st.LaunchSeen`) touch objects the writing realm allocated.
- §3.3 /p/ immutability: decisions, hlroute and hyperlane keep no mutable package state (hyperlane's `zeroes` is computed at init and only read); `tree hl.Tree` is hlmailbox's own value, so `Insert` writes hlmailbox's storage.
- §8 conversion guards: no conversion to a foreign /r/-declared type anywhere; the one cross-realm conversion, `string(body)` of hlmailbox.Process's return (hlgnot.gno:242, hlbubble.gno:227), is exercised by both route tests' Process paths.
- §9 panics vs errors across boundaries: every closure returns an error only before any write (the 14-day deadline; Launch's "launched already"), everything else panics; a verifier's error becomes a panic after `done.Set`, which the cross-boundary abort reverts; `revive` appears only in tests.
- §11.3 callbacks and interfaces: no exported realm function takes a func value; p/hlroute's `DraftVoid(seatOf)`, `Ledger.Each(func(*Decision))` and `Env` are reachable only through unexported state; the one interface entry point is `RegisterVerifier` (X2); `Draft.Params` and the mailbox's private param types cannot be forged by a foreign realm (construction-time check).
- Guide §5.5 and reentrancy: hlgnot's envelope is exact and read once before the fee moves; coin sends and grc20votes' `move` run no code (TransferFrom debits the allowance before the move); hlbubble checks the balance delta; no banker is stored, a fresh RealmSend banker per payment; a verifier reached from `Process` holds no cur, so it can cross into nothing.
- Guide "authorization by address vs by realm": seats and the treasurer by address (user keys), routes, the DAO and the successor by exact pkgpath, so a sub-identity is refused there (X1 is the one prefix match); the route powers (`MarkDone`, `ClearFlags`, `VacateSeat`, `AddRoute`) are exercised only inside GovDAO decisions, never from `Claim`.
- Review §10/§11: every Render path parses ids, nonces and offsets and never panics on bad input; every rendered string is a validated id, address, number or chain-validated pkgpath; `Balance()` and `Balances()` read one denom with `GetCoin`.
- Bounds, clocks, overflow and the tests' blind spots: flags ≤ 6 seats × 3 functions × routes, routes grow only by migration, id lists ≤ 256, pages capped (R6, R13, R14 hold); every clock is block time; overflow guarded where an amount can be chosen (`Credit`, `sync sequence`); no test runs an /e/ caller against `TransferRemote` (a CodeRealm stands in), registers from a sub-identity (X1), or activates a /p/-typed verifier (X2).

## Verdict

The realms are built as the documents ask: every mutator is a crossing function reading its own `cur`, the one unsafe call is the envelope read in its prescribed pairing, no realm value is stored, the GovDAO closures run under their own realms with the proxy as Previous, and the route state lives under the route that allocated it. Two findings, both at the mailbox's open registration: X1 (medium) — v1.2.0's sub-realm tokens let one realm register verifiers without bound, and the mailbox's json and page, which the watch reads, fail for good; X2 (low) — a /p/-typed verifier GovDAO activated could rewrite the proposed signer set through the slice it is handed. Both fixes are one line in mailbox.gno.
